# ADR-GOV-0013: PTO ISA 0.58.6.0 to 0.58.7 compatibility and release identity

## Summary

Advance the post-`v0.58.6.0` architecture to PTO ISA `0.58.7`, with first publication identity `0.58.7.0` and encoding ABI `pto-isa-0.58.7-mode-function-v1`. This record classifies the accumulated accepted delta and enumerates its exact changed NDF and ASL-unit identities. It does not define instruction semantics.

## Context

The immutable `v0.58.6.0` baseline is `dea0b75e803cffa873982c90f9aa0cd17c6d243b`. Subsequent accepted work changed instruction inventory, bundle schemas, tile layouts, numeric conversion, memory ordering, fault behavior, and TileOp assembly. Continuing to identify this moving draft as `0.58.6.0` would conflate incompatible contracts. Issue #270 tracks the first post-baseline publication.

## Decision

Use architecture `0.58.7` and first publication `0.58.7.0`. Use the published `v0.58.6.0` commit as the release-selection baseline. The affected metadata above is the exact baseline-to-candidate digest drift for the owning NDF clauses and ASL units, including retired baseline identities. It is a release coverage inventory, not a second source of architectural meaning. Each topic's current ASL/NDF remains authoritative.

## Normative delta

No ASL or NDF semantics are introduced by this compatibility record. The changed contracts remain in their current accepted ASL/NDF owners and topic ADRs. The publication identity and compatibility classification apply to that complete delta only after exact-commit release verification succeeds.

## Externally visible interface delta

The direct Tile operation set, command and TileOp assembly surfaces, CUBE and Shared layout contracts, numeric conversions, memory-order model, and first-fault behavior differ from the baseline. `BSTART.CALL` is retired. `TEXPDIF` and other post-baseline operations are additions. The encoding projection changes both for accepted assignments and for the new ABI identity. Binaries and generated assembly bearing the old identity must not be silently relabeled.

## Defaults and intentionally unspecified behavior

Defaults, faults, and intentionally unspecified cases remain exactly those stated by the current owning ASL/NDF. This decision adds no compatibility decoder, target-specific behavior, or inferred precondition.

## Compatibility and dependent-toolchain impact

This is a **breaking** architecture boundary relative to `v0.58.6.0`. Consumers requiring the old memory, fault, bundle, or operation contracts stay pinned to that release. Consumers moving to `0.58.7.0` must rebuild and relink binaries with the new exact ELF identity, regenerate TileOp assembly as needed, update the LLVM PTO ISA identity and ASL-MODEL lock, and satisfy the changed-instruction model cases. Source review determines the required migration but cannot make an old-identity binary valid under the new release. A matching ABI name or encoding fingerprint alone never proves semantic compatibility.

## Alternatives considered

A publication revision under architecture `0.58.6` was rejected because accepted post-baseline changes alter software-visible behavior and inventory. Reusing the old ABI was rejected because it would blur binary identity. A release gate waiver was rejected because the cross-repository closure and exact-head evidence remain mandatory.

## Risks and mitigations

The broad delta can hide a missing downstream case or stale generated projection. The release-selection checker requires exact changed NDF and ASL-unit coverage; preflight binds the PTO, LLVM, and ASL-MODEL identities; the protected release run validates the whole tuple and artifacts. Any later ASL edit changes the drift set and requires updating this inventory and reviewing the resulting head.

## Implementation obligations

- Regenerate the 0.58.7 specification identity, catalogs, numeric evidence, release selection, changelog, and release manifest from their owners.
- Align LLVM and ASL-MODEL to the final encoding projection and candidate lock, with changed-instruction cases.
- Resolve site and evidence failures before freezing the exact candidate tuple.

## Verification obligations

Each repository lands a signed, independently reviewed commit. The protected GitHub Release workflow must validate the final exact tuple, every required AVS point, site artifact, model closure payload, and artifact certification. No local or partial result authorizes publication.

## Release consequences

The first eligible tag is `v0.58.7.0` after a successful exact-head release run and publication handoff. Existing tags are immutable. This ADR does not itself authorize tagging or publication.
