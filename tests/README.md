# Tests

The test directories cover PTO architecture semantics and the pinned ASLRef
toolchain.

## `asl/`

Executable feature and boundary tests for the normative PTO model. Every test
point is one `.asl` file below the exact mirror of its primary ASL owner:

```text
asl/<surface>/<classification>/<unit>.asl
tests/asl/<surface>/<classification>/<unit>/<PTO-TEST-ID>.asl
```

Each file contains exactly one `PTO-TEST` JSON record, one stable ID, and one
integer `main()` that returns zero on success. Test-local helpers are allowed;
calling a helper owned by another test file is not. Multiple independent test
points may share one primary ASL owner.

Validate metadata, source ownership, unit coverage, and executable NDF coverage
without ASLRef:

```bash
./scripts/check-asl-tests
```

Inspect the exact-head, sorted, paged scheduling matrix with
`scripts/print-asl-test-matrix`. Execute one test point with
`scripts/run-asl-test --id <PTO-TEST-ID>`; its assembled program and result are
isolated below `build/asl-test-results/<PTO-TEST-ID>/`. The manual release flow
uses the same matrix and individual runner, so parallel scheduling never changes
the coverage claim.

Canonical compile/decode points are generated by
`scripts/generate-mnemonic-avs.py`; focused behavior tests remain independent
checked-in sources. Git history owns the retired migration-only sources; the
active tree contains only independently identified mirrored test points.

## `canary/`

Toolchain checks for the pinned ASLRef, exercised by
`make toolchain-check`.

| Fixture | Expected | Asserted diagnostic |
| --- | --- | --- |
| `accept.asl` | strict type-checking succeeds | — |
| `reject-parse.asl` | parsing fails | `ASL Grammar error:` |
| `reject-type.asl` | strict type-checking fails | `ASL Type error:` |
| `exec-pass.asl` | `main` returning zero exits successfully | — |
| `exec-fail.asl` | a run-time failure exits nonzero | `ASL Dynamic error:` |

Rejections are matched against their diagnostic class, not only a nonzero exit.
Otherwise a fixture failing in the wrong phase could satisfy a canary without
testing the intended parser, type-checker, or interpreter behavior.

The expectations are tied to the commit in `.aslref-version`. Update and
explain affected fixtures whenever that pin changes.

See `CONTRIBUTING.md` and `.codex/skills/pto-asl/references/formal-quality.md`
for the evidence required by normative changes.
